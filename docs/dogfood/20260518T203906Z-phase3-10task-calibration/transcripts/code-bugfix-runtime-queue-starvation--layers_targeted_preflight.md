### Diagnosis
The issue was caused by `Dispatcher::acquire` performing an unconditional `try_dequeue` from the `WeightedFairQueue`. If all worker slots were full, or if a standard task was dequeued but only reserved-for-critical slots were available, the dispatcher would re-enqueue the task and return `None`. However, the `WeightedFairQueue` had already advanced its internal round-robin position. This meant that the "turn" for that priority was wasted, forcing it to wait for a full cycle of critical tasks (8 turns) before its next opportunity. Under heavy load, standard tasks could be repeatedly dequeued and re-enqueued, effectively being locked out of the processing loop.

### Fix
I implemented a conditional dequeueing mechanism:
1.  Modified `WeightedFairQueue` to support `try_dequeue_conditional`, which only pops an item from the queue if a worker slot is actually available for that item's priority.
2.  Updated `Dispatcher::acquire` to check for slot availability *before* attempting to dequeue.
3.  Ensured that the round-robin counter is only advanced when a task is successfully dequeued and can be processed, preserving the configured 8:1 ratio even when the dispatcher is saturated.
